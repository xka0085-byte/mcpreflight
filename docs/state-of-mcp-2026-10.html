How healthy was the ecosystem at the 2026-11-02 snapshot? We ran a read-only initialize + tools/list check against the 35,327 remote endpoints that sweep returned from the official MCP Registry: 20,701 (58.6%) completed a clean handshake, 10,236 (29%) answered with a confirmed authentication gate, 4,223 (12%) gave no anonymous response, and 167 (0.5%) failed outright. Among responders we logged 219,101 property-level schema findings, and 82.3% negotiate the 2025-06-18 protocol revision. Every number is reproducible with one open-source command, and the raw counts sit in mcp-state-summary.json.

What we did

We swept the official MCP Registry for active servers with a remote (HTTP) transport and sent exactly two JSON-RPC requests to each endpoint our complete 2026-11-02 sweep returned, 35,327 of them: initialize and tools/list. We validated protocol negotiation and every tool's input/output JSON Schema. No tool was ever called, no authentication was attempted, no data beyond the handshake was read. The whole thing is open source and one command reproduces any single result:

npx @eidonze/mcpreflight schema <endpoint-url>

Findings

1. Four in ten endpoints our sweep returned cannot be used anonymously — and after 0.3.0 we can say why. 14,626 of 35,327 remote endpoints (41.4%) did not complete a clean initialize + tools/list handshake. The bucket is no longer one blob: 29% are a confirmed authentication gate (10,236 endpoints; 7,586 verified against live RFC 9728 metadata or a 401 challenge, 2,623 detected), 12% gave no anonymous response at all (4,223), and only 0.5% (167) answered with something that is actually broken. The registry's real blind spot is not broken servers, it is unlabelled auth walls: the split is now reproducible from the outside, but the registry itself still publishes no field that an agent could read instead of probing.
2. Protocol adoption is fragmented — and running an older revision does not make a server sicker. Of the 20,743 servers that negotiated a protocol version, 82.3% run 2025-06-18 and 13.6% are still on 2025-03-26. Only 117 (0.6%) speak the newest revision (2026-07-28). But the pass rate barely moves with age: 2025-06-18 passes at 99.9%, 2024-11-05 — a year behind — still passes at 98.3% across 592 endpoints. Version lag is a feature-adoption question, not a health question, and counting "outdated servers" as a quality metric would be wrong.

3. Schema hygiene is the quiet tax — and the defects are far more concentrated than the totals suggest. The dominant schema finding is a missing description on an input property: 219,101 property-level findings across 8,421 servers (23.8% of the registry). Tool descriptions are what an LLM reads to decide when and how to call a tool. The outright breakage is tiny and clustered: 146 servers return a tools/list that is not a tool list at all, 125 return an invalid initialize, and 27 malformed inputSchema objects come from just 3 servers. Fixing the ecosystem's worst schemas is a few dozen pull requests, not a campaign.
4. The community index and the official registry disagree. We cross-checked the largest community awesome-list (4,537 GitHub repo links) against registry data: only 226 of its links correspond to servers we have registry scan coverage for, and 85 of those do not pass a clean anonymous handshake. Discovery is fragmented across at least two inconsistent indexes, and a listing on the popular list carries no information about whether an endpoint works.
5. A third-party proxy sits inside the official registry. 216 registry entries (0.6%) do not point at a maintainer's own server but at server.smithery.ai proxy URLs. All 216 refused a clean anonymous handshake — 0% completed initialize + tools/list (26 AUTH_GATED, 190 UNKNOWN), against 59% that pass across the other 35,111 endpoints. Most of that gap is by design: the proxy expects a per-server config and key. The consequence is the same either way: an agent, or any independent auditor, following the official registry cannot verify these 216 servers at all without first signing up with a third party — and cannot tell auth-by-design from dead-on-arrival. We started this comparison after a maintainer flagged auto-registered placeholder entries (kirbah/mcp-youtube#290); our data cannot confirm or refute what sits behind the proxy, only that it is unverifiable from the outside.
6. The x402 economy is already inside the registry — and healthier than average. 1,583 endpoints reference x402 / HTTP-402 payments in their registry metadata. They pass a clean anonymous handshake at 65.6% (1,039 of 1,583), against the 58.6% baseline of the same sweep; 537 remain unverifiable anonymously (30 AUTH_GATED, 507 UNKNOWN) and 7 fail outright. The gap has a mechanical explanation: a payment server whose challenge flow is malformed fails its first agent transaction, so this cohort ships cleaner handshakes. As agent-payment volume grows (Coinbase has reported x402 transaction counts in the hundreds of millions), this is the cohort where challenge-shape drift and misconfiguration will concentrate — 65.6% is today's baseline, and we now track challenge-shape drift on these endpoints as a dedicated check.

Limitations (read this before quoting us)

  • Anonymous handshake only. Servers behind OAuth are not broken — but the registry does not label them, so the 41.4% figure is an upper bound on breakage, not an exact count. Of that share, 29 percentage points are a confirmed auth gate that is working as designed: an anonymous probe cannot use those servers, but they are not broken. The only outright breakage in this sweep is the 0.5% that returned an invalid handshake.
  • Static schema checks do not predict model tool selection and do not prove behavior across clients.
  • One point in time (2026-10-11), re-scanned weekly; per-server history and diffs are planned.
  • If your server is listed as "no handshake" and requires auth by design: that's expected — you can ignore it, or reply on the directory to be excluded.

What this scan does not cover

One limitation used to sit next to the headline number, and it is now fixed rather than explained. The 9,991 figure we published in October was what a scanner capped at 300 cursor pages returned; it was never the size of the registry. The cap was the constraint: a complete traversal walks 1,984 cursor pages and returns 198,345 registry entries, of which 52,765 are the latest version of an active server and 35,327 carry a remote HTTP transport. Those 35,327 are what this page reports, scanned in one pass rather than assembled from a partial cache. The public API still exposes no total, so any number has to come from a traversal; the difference now is that the script producing it is in the repository, so every figure here can be re-derived instead of trusted.

A second measurement sidesteps the question by sampling instead of sweeping: 500 endpoints drawn at random on 2026-10-29 from the then-current 34,190-endpoint census, of which 316 completed a clean anonymous handshake (63.2%, 95% CI 58.9-67.3). Method and raw responses: mcpreflight-audit.pages.dev. The two numbers are not interchangeable. The census describes the endpoints our sweep reached; the sample estimates the wider registry. Do not average them and do not quote one as the other.
