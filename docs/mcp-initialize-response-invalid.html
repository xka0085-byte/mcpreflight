My MCP server returns an invalid initialize response

The handshake is all-or-nothing: if initialize returns a payload a client considers malformed, nothing after it is ever reached. In the 2026-11-02 sweep, 125 of 35,327 remote endpoints (0.4%) answered the handshake with a response that violates the expected shape.

How common it is

  • Endpoints with an invalid initialize response — 125 of 35,327 (0.4%)
  • Endpoints that completed the handshake cleanly — 20,701 of 35,327 (58.6%)
  • Endpoints gated behind authentication — 10,236 (29%)

What it means

The usual causes are a protocolVersion the server does not actually speak, a capabilities or serverInfo object with the wrong shape, or a payload wrapped in an extra envelope so the client sees no result where it expects one. Because the failure happens at the first message, the client-side error is often a generic connection closed, which sends people looking at the transport instead of the response body.

Check it in one command

npx @eidonze/mcpreflight schema https://your-server.example.com/mcp

The check is read-only. It performs the handshake steps and reports which one answered what; it does not authenticate, mutate, or write anything to the server.

Three steps

  1. Capture the exact JSON-RPC body returned by initialize and check for result.protocolVersion, result.capabilities and result.serverInfo.
  2. Compare the negotiated protocolVersion against the one the client requested. Echoing an unsupported version is a common way to fail a strict client.
  3. Send notifications/initialized only after a successful response, then confirm tools/list answers — a server that skips the notification often looks invalid from the outside.
