My MCP server closes the connection during initialize

In the 2026-11-02 sweep, 4,250 of 35,327 remote endpoints (12%) returned nothing at all to a well-formed initialize: no JSON-RPC payload, no error, no HTTP status the probe could use. The streamable HTTP transport expects a POST that stays open long enough to answer.

How common it is

  • Endpoints with no response to initialize — 4,250 of 35,327 (12%)
  • Endpoints that did complete a clean anonymous handshake — 20,701 of 35,327 (58.6%)
  • Endpoints publishing at least one tool — 20,722

What it means

No response is a transport problem before it is an MCP problem. The three causes worth ruling out, in order, are the wrong path for the transport (a /sse listener behind a /mcp URL), a proxy or CDN that buffers or drops the streaming response, and a process that exits while handling the request. Because nothing comes back, a client cannot tell these apart either — which is why the census records it as its own state instead of folding it into failures.

Check it in one command

npx @eidonze/mcpreflight schema https://your-server.example.com/mcp

The check is read-only. It performs the handshake steps and reports which one answered what; it does not authenticate, mutate, or write anything to the server.

Three steps

  1. Confirm the URL points at the transport you implemented. A streamable HTTP endpoint must accept POST with Accept: application/json, text/event-stream; a stdio-only server has no HTTP surface at all.
  2. Curl the endpoint from outside your network. If it answers locally but not publicly, the gap is the proxy, the CDN buffering rule, or a firewall dropping long-lived responses.
  3. Check that the process survives the request: log the exit path and the unhandled rejection handler, since a crash mid-request looks identical to a closed stream from the client side.
