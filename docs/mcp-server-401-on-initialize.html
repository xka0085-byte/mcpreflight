My remote MCP server returns 401 on initialize

In the 2026-11-02 sweep of the official MCP Registry, 10,236 of 35,327 remote endpoints (29%) answered our read-only probe with a 401 or with a live OAuth discovery document instead of an anonymous handshake. 7,586 of those carry a gate we confirmed against RFC 9728 resource metadata or an actual 401 challenge; the rest are classified from response headers alone.

How common it is

  • Remote endpoints that gate anonymous access — 10,236 of 35,327 (29%)
  • Gate confirmed against live metadata or a 401 challenge — 7,586
  • Endpoints that answered nothing at all — 4,223 of 35,327 (12%)

What it means

A 401 on initialize is usually the server working as designed: it wants an OAuth token before it will talk to anyone, and the MCP authorization spec expects that token to be discovered from /.well-known/oauth-protected-resource. The failure worth chasing is not the 401 itself but a 401 with no way to obtain a token, or a client that cannot complete the discovery chain. This is why the census keeps AUTH_GATED separate from UNKNOWN: an endpoint that refuses and explains itself is healthy, an endpoint that refuses silently is not.

Check it in one command

npx @eidonze/mcpreflight schema https://your-server.example.com/mcp

The check is read-only. It performs the handshake steps and reports which one answered what; it does not authenticate, mutate, or write anything to the server.

Three steps

  1. Send a bare POST initialize and read the status line together with the WWW-Authenticate header. A 401 that names a resource metadata URL is a working gate.
  2. Fetch that metadata document. If it 404s while the server still demands a token, clients have no path to authenticate — publish the document before shipping the gate.
  3. Re-run the same check with a token against a second endpoint to confirm the tool surface is reachable, not just the front door.
