The model never calls my MCP tool

Descriptions are the only thing a model has to decide whether to call a tool. In the 2026-11-02 sweep, 8,421 of the 20,722 endpoints that published tools (40.6%) left at least one parameter without a description — 219,101 individual properties across those schemas carried no description. Another 15 endpoints left a whole tool undescribed. The two counters are separate: a server can be in both, so they do not add up to one population.

How common it is

  • Endpoints publishing tools — 20,722
  • Endpoints with at least one property missing a description — 8,421 (40.6% of those)
  • Individual properties missing a description — 219,101
  • Endpoints with a tool that has no description of its own — 15 endpoints, 53 tools

What it means

A tool with no description is still listed, still valid against the schema, and still invisible in practice: the model has to infer the purpose from the name alone. Property descriptions matter more than most servers assume — they are argument-level documentation, and a required string called q with no description is a guess the model will often decline to make. This is the single largest hygiene gap in the public registry, and it is also the cheapest to fix.

Check it in one command

npx @eidonze/mcpreflight schema https://your-server.example.com/mcp

The check is read-only. It performs the handshake steps and reports which one answered what; it does not authenticate, mutate, or write anything to the server.

Three steps

  1. List every tool and check that each one has a non-empty description that states when to use it, not only what it does.
  2. Walk each inputSchema.properties entry and describe every property, including the obvious ones — the model does not share your context.
  3. Re-read a description as if you were the model deciding between two tools. If both readings sound identical, the description is not doing its job.
