Why this report exists

The ERC-8004 registry now lists hundreds of thousands of on-chain agents, and its spec deliberately leaves reputation aggregation to third parties. What is missing is the boring part: does the registered identity actually resolve to a working endpoint, does the registration file still say what the chain says it says, and can an integrator check all of that before plugging an agent into a workflow. This is a small sample of exactly that check. It is not a trust score, it is a list of what we could and could not verify, with reasons.

Each agent gets one of five verdicts, from strongest to weakest: fully consistent (registration declares the endpoint, a clean anonymous MCP handshake succeeds), partially consistent (handshake started but did not complete cleanly), conflict (declared and observed facts disagree), unverifiable (endpoint exists but we could not complete verification, reason stated), missing data (nothing declared to check). A record not being found is never treated as fraud.

Findings

1. Batch minting inflates the on-chain agent count. Our 88 sampled tokens resolve to just 40 unique MCP endpoints. One endpoint (api.signalbound.art/mcp) is claimed by 18 separate ERC-721 tokens; another by 16. Five endpoints account for 50 of the 88 tokens. Anyone consuming the registry by token count today overcounts distinct agents — in this sample, by more than 2×.
2. The 8004 ecosystem and the official MCP Registry do not overlap — at all. We cross-matched all 40 endpoints against the 9,991 endpoints in the Trust Directory (official MCP Registry scan): zero exact-URL matches, zero host-level matches in this sample. Two agent ecosystems currently index disjoint populations. A buyer checking one gets no information about the other.
3. A passing handshake is a low bar, and mostly a free-tier bar. 24 of 40 endpoints completed a clean anonymous MCP handshake. 17 of those 24 run on *.vercel.app free-tier subdomains. Identity verification on-chain plus a working endpoint says nothing about who operates the deployment, how long it will live, or whether behavior matches claims over time. The consistent-but-cheap cohort is exactly where a behavior-evidence layer has work to do.
4. Registration files are mostly live — when you can reach them. 37 of 40 registration files were independently re-fetched, and all 37 still declare the same MCP endpoint as the on-chain index cache. Only 1 is byte-for-byte identical to the cache — the rest differ in JSON serialization (field order, formatting), not in declared endpoints. 3 use ipfs:// URIs that public gateways rate-limited during our window, so their declarations rest on the index cache only and are marked unverifiable in the table.

Method

  • Sampling. 88 tokens pulled from the 8004scan explorer API (api.8004scan.io), biased toward agents declaring MCP support (has_mcp=true, mainnets only) plus active and top-scored cohorts. 40 unique MCP endpoints remained after deduplication. This is a convenience sample, not a random one.
  • Declaration side. For each agent: on-chain registration metadata (via 8004scan), the registration file URI it points to, and the declared MCP service entry. Registration files were independently re-fetched and compared against the index cache.
  • Observation side. Each declared endpoint received exactly two JSON-RPC requests: initialize and tools/list, via mcpdoctor schema 0.1.5 (MIT, zero dependencies). No tool was ever called, no authentication attempted, no payment signed.
  • Cross-match. All 40 endpoints were matched against the 9,991-endpoint Trust Directory scan by exact URL and by host.
  • Reproduce any row:
npx @eidonze/mcpdoctor schema <endpoint-url>

Limitations (read this before quoting us)

  • Anonymous checks only. Endpoints returning 401 (auth required) or 402 (payment required) are counted as unverifiable, not broken. One endpoint failed initialize with HTTP 402 — that is x402 working as designed, not a dead agent.
  • One point in time. Probes ran 2026-10-12 08:00 to 2026-10-12 08:03 UTC. Endpoints change; a weekly re-run is planned.
  • No behavior beyond the handshake. We never invoked a tool. Consistency here means the declared endpoint speaks MCP and lists tools, nothing stronger.
  • Index cache dependency. Registration content came from 8004scan's cache for the 3 IPFS-hosted files we could not re-fetch through rate-limited public gateways.
  • Ownership not resolved. We did not verify that the owner address controls the endpoint domain (DNS/ERC-1271 binding checks are future work), so "fully consistent" does not mean "operator verified".
  • Small, biased sample. 88 tokens is a sliver of the registry, selected for declared MCP support. The batch-minting finding is arithmetic on this sample, not an estimate for the whole registry.
  • 0 conflicts and 0 missing-data rows in this sample is a property of the sampling, not evidence that conflicts do not exist.

What we would build next

This page is the v0 of that loop: sample, verify, publish, repeat weekly, and let integrators diff an agent's declared self against its observed behavior over time. If you maintain an agent directory, a marketplace, or a workflow that consumes 8004 agents and this kind of pre-integration evidence would change a decision you make, we would like to hear from you — open an issue.
