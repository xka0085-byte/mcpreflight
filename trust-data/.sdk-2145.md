Adding field data from the client side, since this directly affects what strict clients see.

We operate a read-only checker (MCP `initialize` + `tools/list` only, never calls tools) that scans the ~10k endpoints registered in the official MCP Registry weekly. Empty or malformed published `inputSchema` is one of the recurring failure shapes we record, and Zod effect-wrapping is a frequent cause — tools list with `{"type":"object"}` or no constraints at all while the server actually requires parameters.

Two observations that may help scoping a fix:

1. The failure is invisible to authors testing with lenient clients, because the model guesses parameters interactively. It only surfaces with schema-validating clients — which is exactly when it looks like the client's bug.
2. It reappears silently after refactors: wrapping an existing `z.object()` in `.refine()`/`.transform()` changes what `tools/list` publishes with no error at registration time. That argues for either a warning at wrap time in the `McpServer` layer, or a documented, explicit pattern for effect-wrapped schemas.

For anyone hitting this in production: it is mechanically detectable before deploy. We gate it in CI (read-only, MIT: https://github.com/xka0085-byte/mcp-doctor). Happy to share aggregate scan stats on empty-`inputSchema` frequency if useful for prioritization.
